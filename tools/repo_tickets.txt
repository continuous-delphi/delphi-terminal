Title: Fix use-after-free risk in queued thread notifications during shutdown
Issue: #22
Status: closed
Labels: bug
Body:
`NotifyOutput` and `NotifyExit` in `TCmdShellProcess` use `TThread.Queue(nil, ...)`
with closures that capture `LOwner` (a raw pointer to the owning `TCmdShellProcess`).
If the shell object is destroyed while queued messages are still pending in the main
thread message queue, the closures execute against freed memory.

**Scenario:** The reader thread queues multiple output notifications. The owner calls
`Terminate` (which waits for thread exit and frees the thread). The destructor
completes. The queued anonymous methods then fire with a dangling `LOwner` pointer,
causing an access violation.

This is most likely to manifest during IDE shutdown or when rapidly closing/reopening
the terminal panel while the shell is producing output.

**Affected code:** `source/Delphi.Terminal.CmdShell.pas` lines 76-101
(`TPipeReaderThread.NotifyOutput` and `TPipeReaderThread.NotifyExit`).

**Possible approaches:**
- Add a guard flag (e.g. `FDestroying`) checked inside each queued closure before
  accessing the owner, protected by a shared reference or critical section
- Switch from `TThread.Queue(nil, ...)` to `TThread.Queue(FReaderThread, ...)` so
  that freeing the thread cancels its pending queued methods
- Use an ref-counted shared-state record so closures can detect owner destruction
- Drain the message queue after `WaitFor` and before freeing the owner

Acceptance criteria:
- [ ] Destroying a `TCmdShellProcess` while output is actively being produced does
      not cause an access violation
- [ ] Rapid close/reopen of the terminal panel does not crash
- [ ] IDE shutdown with active shell output does not crash
- [ ] Existing tests continue to pass

Title: Multi-byte UTF-8 characters can split across pipe reads
Issue: #24
Status: closed
Labels: bug
Body:
The reader thread in `TPipeReaderThread.Execute` reads raw bytes from the
pipe and immediately decodes them in a single call:

```delphi
NotifyOutput(FEncoding.GetString(Bytes));
```

A multi-byte UTF-8 character (2-4 bytes) can be split across two `ReadFile`
calls. The first call produces a replacement character for the incomplete
sequence; the trailing bytes in the next call also produce a replacement
character. Result: non-ASCII text (accented characters, CJK, emoji, Unicode
file paths) randomly corrupts depending on where the read boundary falls.

**Affected code:** `source/Delphi.Terminal.CmdShell.pas`, `TPipeReaderThread.Execute`
(lines 103-117).

**Fix:** Accumulate a small leftover-byte buffer between reads. After each
`ReadFile`, append the new bytes to the leftover buffer, decode only complete
characters, and carry over any trailing incomplete byte sequence for the next
read. For UTF-8, an incomplete trailing sequence can be detected by checking
the lead-byte pattern of the final bytes.

Acceptance criteria:
- [ ] Multi-byte UTF-8 characters split across read boundaries decode correctly
- [ ] Single-byte ASCII output is unaffected
- [ ] OEM codepage path (CMD) still works correctly
- [ ] Unit test verifies correct decoding of a split multi-byte character
- [ ] Existing tests continue to pass

Title: Dockable form not restored on IDE restart -- missing desktop registration
Issue: #35
Status: closed
Labels: bug
Body:
When the delphi-terminal window is docked and the user saves the default
desktop, the terminal does not reappear in its docked position after
restarting RAD Studio. The IDE saves the dock state (via `DeskSection`,
`AutoSave`, `SaveStateNecessary`) but has no way to recreate the form
on startup because the class is not registered with the desktop manager.

**Root cause:** The plugin never calls `RegisterDesktopFormClass` or
`RegisterFieldAddress` (from the `DeskUtil` unit). Without these, the
IDE records the form's dock state but cannot instantiate it during
desktop restore.

**Reference implementations:**
- GExperts `GX_IdeDock.pas` -- wraps both calls in an `IIdeDockManager`
  interface; sets `DeskSection := Name` so the section matches the
  form's component name.
- DTerminal `uMain.pas` (lines 63-68) -- calls both in its `Register`
  procedure with a stable identifier.

**Required changes:**

1. Add `DeskUtil` to the uses clause of `Delphi.Terminal.Plugin.Registration`.
2. In `Register`, after the wizard/options/keybinding registration, call:
   - `RegisterDesktopFormClass(TfrmDelphiTerminalDock, ID, ID)` where
     `ID` is a stable string matching `DeskSection`.
   - `RegisterFieldAddress(ID, @FInstance)` -- requires exposing the
     `FInstance` unit variable (or moving it to a shared location).
3. In `Delphi.Terminal.Plugin.DockForm`:
   - Set `Name := ID` in the constructor so the VCL component name
     matches the desktop section.
   - Ensure `DeskSection` uses the same identifier (currently
     `'continuous_delphi_delphi_terminal'` -- keep this value but use
     it consistently as a named constant).
   - The constructor must handle IDE-initiated creation (the IDE calls
     `Create(nil)` with no prior `ShowInstance` call) -- assign
     `FInstance := Self` inside the constructor so the singleton is set
     regardless of creation path.
4. In `Delphi.Terminal.Plugin.Lifecycle`:
   - Call `UnregisterFieldAddress(@FInstance)` during shutdown, before
     freeing the form.

**Consistency note:** The `DeskSection` value, the `Name` property, and
the identifiers passed to `RegisterDesktopFormClass` /
`RegisterFieldAddress` must all be the same string.

Acceptance criteria:
- [ ] `RegisterDesktopFormClass` and `RegisterFieldAddress` are called
      during plugin registration
- [ ] `UnregisterFieldAddress` is called during plugin shutdown
- [ ] Form `Name`, `DeskSection`, and registration identifier are the
      same constant string
- [ ] Docking the terminal, saving the desktop, and restarting the IDE
      restores the terminal in its docked position
- [ ] `ShowInstance` and `ToggleInstance` continue to work correctly
      after the registration changes
- [ ] The form constructor handles both user-initiated and IDE-initiated
      creation paths

Labels: bug
Body:

the same pattern.

Fix: wrap each `StartShell` call in `Form.Main.pas` with try/except and
call `ShowStartupError` on failure, matching the IDE plugin approach.

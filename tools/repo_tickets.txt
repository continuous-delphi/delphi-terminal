Title: Fix use-after-free risk in queued thread notifications during shutdown
Issue: #22
Status: closed
Labels: bug
Body:
`NotifyOutput` and `NotifyExit` in `TCmdShellProcess` use `TThread.Queue(nil, ...)`
with closures that capture `LOwner` (a raw pointer to the owning `TCmdShellProcess`).
If the shell object is destroyed while queued messages are still pending in the main
thread message queue, the closures execute against freed memory.

**Scenario:** The reader thread queues multiple output notifications. The owner calls
`Terminate` (which waits for thread exit and frees the thread). The destructor
completes. The queued anonymous methods then fire with a dangling `LOwner` pointer,
causing an access violation.

This is most likely to manifest during IDE shutdown or when rapidly closing/reopening
the terminal panel while the shell is producing output.

**Affected code:** `source/Delphi.Terminal.CmdShell.pas` lines 76-101
(`TPipeReaderThread.NotifyOutput` and `TPipeReaderThread.NotifyExit`).

**Possible approaches:**
- Add a guard flag (e.g. `FDestroying`) checked inside each queued closure before
  accessing the owner, protected by a shared reference or critical section
- Switch from `TThread.Queue(nil, ...)` to `TThread.Queue(FReaderThread, ...)` so
  that freeing the thread cancels its pending queued methods
- Use an ref-counted shared-state record so closures can detect owner destruction
- Drain the message queue after `WaitFor` and before freeing the owner

Acceptance criteria:
- [ ] Destroying a `TCmdShellProcess` while output is actively being produced does
      not cause an access violation
- [ ] Rapid close/reopen of the terminal panel does not crash
- [ ] IDE shutdown with active shell output does not crash
- [ ] Existing tests continue to pass

Title: Multi-byte UTF-8 characters can split across pipe reads
Issue: #24
Status: closed
Labels: bug
Body:
The reader thread in `TPipeReaderThread.Execute` reads raw bytes from the
pipe and immediately decodes them in a single call:

```delphi
NotifyOutput(FEncoding.GetString(Bytes));
```

A multi-byte UTF-8 character (2-4 bytes) can be split across two `ReadFile`
calls. The first call produces a replacement character for the incomplete
sequence; the trailing bytes in the next call also produce a replacement
character. Result: non-ASCII text (accented characters, CJK, emoji, Unicode
file paths) randomly corrupts depending on where the read boundary falls.

**Affected code:** `source/Delphi.Terminal.CmdShell.pas`, `TPipeReaderThread.Execute`
(lines 103-117).

**Fix:** Accumulate a small leftover-byte buffer between reads. After each
`ReadFile`, append the new bytes to the leftover buffer, decode only complete
characters, and carry over any trailing incomplete byte sequence for the next
read. For UTF-8, an incomplete trailing sequence can be detected by checking
the lead-byte pattern of the final bytes.

Acceptance criteria:
- [ ] Multi-byte UTF-8 characters split across read boundaries decode correctly
- [ ] Single-byte ASCII output is unaffected
- [ ] OEM codepage path (CMD) still works correctly
- [ ] Unit test verifies correct decoding of a split multi-byte character
- [ ] Existing tests continue to pass

Title: Dockable form not restored on IDE restart -- missing desktop registration
Issue: #35
Status: closed
Labels: bug
Body:
When the delphi-terminal window is docked and the user saves the default
desktop, the terminal does not reappear in its docked position after
restarting RAD Studio. The IDE saves the dock state (via `DeskSection`,
`AutoSave`, `SaveStateNecessary`) but has no way to recreate the form
on startup because the class is not registered with the desktop manager.

**Root cause:** The plugin never calls `RegisterDesktopFormClass` or
`RegisterFieldAddress` (from the `DeskUtil` unit). Without these, the
IDE records the form's dock state but cannot instantiate it during
desktop restore.

**Reference implementations:**
- GExperts `GX_IdeDock.pas` -- wraps both calls in an `IIdeDockManager`
  interface; sets `DeskSection := Name` so the section matches the
  form's component name.
- DTerminal `uMain.pas` (lines 63-68) -- calls both in its `Register`
  procedure with a stable identifier.

**Required changes:**

1. Add `DeskUtil` to the uses clause of `Delphi.Terminal.Plugin.Registration`.
2. In `Register`, after the wizard/options/keybinding registration, call:
   - `RegisterDesktopFormClass(TfrmDelphiTerminalDock, ID, ID)` where
     `ID` is a stable string matching `DeskSection`.
   - `RegisterFieldAddress(ID, @FInstance)` -- requires exposing the
     `FInstance` unit variable (or moving it to a shared location).
3. In `Delphi.Terminal.Plugin.DockForm`:
   - Set `Name := ID` in the constructor so the VCL component name
     matches the desktop section.
   - Ensure `DeskSection` uses the same identifier (currently
     `'continuous_delphi_delphi_terminal'` -- keep this value but use
     it consistently as a named constant).
   - The constructor must handle IDE-initiated creation (the IDE calls
     `Create(nil)` with no prior `ShowInstance` call) -- assign
     `FInstance := Self` inside the constructor so the singleton is set
     regardless of creation path.
4. In `Delphi.Terminal.Plugin.Lifecycle`:
   - Call `UnregisterFieldAddress(@FInstance)` during shutdown, before
     freeing the form.

**Consistency note:** The `DeskSection` value, the `Name` property, and
the identifiers passed to `RegisterDesktopFormClass` /
`RegisterFieldAddress` must all be the same string.

Acceptance criteria:
- [ ] `RegisterDesktopFormClass` and `RegisterFieldAddress` are called
      during plugin registration
- [ ] `UnregisterFieldAddress` is called during plugin shutdown
- [ ] Form `Name`, `DeskSection`, and registration identifier are the
      same constant string
- [ ] Docking the terminal, saving the desktop, and restarting the IDE
      restores the terminal in its docked position
- [ ] `ShowInstance` and `ToggleInstance` continue to work correctly
      after the registration changes
- [ ] The form constructor handles both user-initiated and IDE-initiated
      creation paths

Title: ConPTY: deferred line wrap (DECAWM) and reliable PTY size sync
Issue: #78
Status: closed
Labels: bug, conpty
Body:
Found during #70 acceptance testing. In ConPTY mode, editing a line that reaches
the right margin corrupts the display. Repro (VCL demo, pwsh tab): type `get` so
PSReadLine shows an inline prediction that fills past the right edge, then press
Backspace -- a spurious newline is inserted and the redraw is misplaced (the
prompt keeps `get` and the remainder of the prediction drops to a new line).

Two root causes:

1. Immediate vs. deferred wrap. `TScreenBuffer.PutChar` advances to the next
   line the instant the cursor passes the last column. Real terminals (DECAWM)
   use a pending-wrap state: after writing the last column the cursor stays
   there, and the wrap happens only when the next printable arrives; any cursor
   movement (CR, BS, CUP, LF) cancels the pending wrap. Without this, an app that
   fills a line exactly and then repositions the cursor desyncs by one row, so
   its erase/move sequences land on the wrong line.

2. PTY size can remain at the 80x24 startup fallback. The session starts before
   the view has its real size; the screen buffer can be resized without the
   pseudoconsole (or a later sync early-returns because the buffer already
   matches), leaving the shell wrapping at 80 columns in a wider window.

Fix: implement pending-wrap in the screen model (cleared on cursor movement /
line feed); track the last size sent to the pseudoconsole and always push the
current view size when it differs, plus a post-layout size sync after start.

Acceptance criteria:
- [ ] Editing a wrapped prediction line in pwsh (type + Backspace) no longer inserts spurious newlines
- [ ] The shell wraps at the view's actual width; resizing reflows correctly
- [ ] Screen-model unit tests cover deferred wrap and its cancellation on cursor movement

Title: ConPTY: OSC 133 shell-integration prompt-state predicate
Issue: #85
Status: closed
Labels: enhancement, conpty
Body:
delphi-terminal writes to the shell programmatically from several places, and in
ConPTY every one of them shares a single precondition: the shell prompt must be
the foreground, not an interactive child. This ticket builds ONE shared
"safe to inject" gate that all of those paths ride. It is NOT a "bring back
Auto-CD" ticket, and the predicate must not be implemented per feature -- each
consumer just calls the one gate.

Riders on the single gate (each keeps its own policy, but they share this one
idle check -- do not reimplement it):
- Saved-command run / preview (#84) -- user-initiated; warn + do not inject when
  not idle.
- Project Dir / File Dir toolbar buttons (#86) -- user-initiated; same policy as
  saved-command run.
- ConPTY Auto-CD -- #83 made Auto-CD legacy-only precisely because there was no
  idle gate. Once this gate exists, a ConPTY tab may auto-cd only when the gate
  reports idle. This is a rider on the gate, not a separate "re-enable Auto-CD"
  feature.
- Paste (`PasteToShell`) is deliberately NOT gated -- pasting into whatever is
  focused is normal terminal behavior.

Primary signal: OSC 133 semantic prompt markers (`ESC]133;A` prompt start,
`;B` command-input start, `;C` command executed, `;D` command finished). The VT
parser already buffers and dispatches OSC (`source/Delphi.Terminal.VTParser.pas`
`DispatchOSC`, line 261, handling Ps 0/2 titles); add a `133` case that tracks
prompt state on the screen model. "Idle at a prompt" == last saw A/B and not yet
C. Because the markers ride the PTY stream from inside the shell, this works for
WSL, where a Windows-side process/Job heuristic cannot see the in-VM child.

OSC 133 is emitted by a shell prompt hook, not by the shell inherently -- none of
cmd/pwsh/PowerShell/WSL send it out of the box (needs PSReadLine/profile snippet,
bashrc integration, clink, etc.). So define the fallback when no 133 markers have
been observed this session. Options to weigh during implementation:
- Job Object active-process count as a fallback busy check (query
  `JOBOBJECT_BASIC_ACCOUNTING_INFORMATION.ActiveProcesses` -- only
  `SetInformationJobObject` is currently declared in `source/WinAPI.ConPty.pas`;
  add `QueryInformationJobObject` + the accounting struct). Shell-only == 1 ==
  idle. Blind spot: WSL (child runs in the VM, not the Windows Job), so pair it
  with the alt-screen flag and prefer OSC 133 when present.
- Alt-screen active (`FScreen` `?1049`) is always a "busy" signal regardless of
  markers.

Expose the predicate as a single method/property the frame and dock form can
call (e.g. `TScreenBuffer`/`TVTParser` prompt-state + a frame-level
`ShellIsIdleAtPrompt`). Half-typed-line note: with 133 present we can also track
"has the user sent a keystroke since the last 133;B" for a stricter idle check;
capture that as a refinement, not a hard requirement.

Implementation notes:
- Parse OSC 133 A/B/C/D in `DispatchOSC`; store prompt state on the screen model.
- Decide and implement the no-marker fallback (Job accounting +/- alt-screen).
- Expose ONE shared idle gate and wire every injection path to it: the
  saved-command paths (#84), the Project/File Dir buttons (#86), and ConPTY
  Auto-CD. Do not duplicate the predicate per feature.

Acceptance criteria:
- [ ] OSC 133 A/B/C/D markers update a prompt-state on the screen model
- [ ] A single shared "shell idle at prompt" gate is exposed for the frame/dock form and consumed by all injection paths (no per-feature reimplementation)
- [ ] When markers are present, an executing command (post-133;C) reports not-idle; a fresh prompt reports idle -- including under WSL
- [ ] A defined fallback covers shells that emit no 133 markers
- [ ] Alt-screen active always reports not-idle
- [ ] Saved commands (#84), the Project/File Dir buttons (#86), and ConPTY Auto-CD all gate on this one predicate
- [ ] Unit tests cover marker parsing and the idle/busy predicate

Title: ConPTY idle gate: three-state + fail-safe hardening (follow-up to #85)
Issue: #87
Status: closed
Labels: bug, conpty
Body:
Review follow-up to #85. As first implemented the gate was a Boolean
(`TScreenBuffer.IsIdleAtPrompt` / `TframeCmdShell.ShellIsIdleAtPrompt`), and its
no-marker fallback returned True (idle) on "no alt-screen and no Windows child".
That is a false-idle -- the exact hazard #83 exists to prevent: a line-oriented
program (a REPL, or Claude Code) sitting at its own prompt has no alt-screen and
(for WSL) no Windows child, so it is indistinguishable from an idle shell. The
fallback can prove BUSY but can never prove IDLE, so it must never return idle.

Governing principle: fail safe (bias to false-busy). False-busy (refuse to inject
when actually idle) is a mild annoyance; false-idle (inject when actually busy) is
the hazard. Every ambiguous/unknown state must resolve to not-idle.

Make the gate three-state -- IDLE / BUSY / UNKNOWN -- not Boolean:
- IDLE: positively established; only OSC 133/633 asserts it (input window: after B,
  before C).
- BUSY: positively established (alt-screen active, Job child count > 1, or 133/633 C).
- UNKNOWN: no markers this session and nothing proves busy. Never collapses to IDLE.

OSC 133 FSM tightened: idle window is "seen B, not yet C" -- require B
(command-input start), not A. A is prompt-start (still rendering the prompt);
injecting in the A->B window races the prompt. Robust mapping: A -> prompt-start
(not idle), B -> input-start (idle-eligible), C -> executing (busy), D -> finished
(not idle). Any BUSY signal overrides an idle marker.

Also:
- Handle OSC 633 (VS Code superset) with the same A/B/C/D semantics -- near-free
  alongside the 133 case; ignore its other subcommands (E command-line, P property).
- Tolerate trailing params: split on ';', switch on the first sub-parameter (A/B/C/D),
  ignore the rest (133;D;<exit>, 133;A;<key=val>).
- Fallback honesty: alt-screen (?1049) -> hard BUSY (rides the PTY stream, so it
  covers WSL full-screen apps too). Job ActiveProcesses > 1 -> BUSY (catches non-WSL
  child REPLs/agents). Neither ever asserts IDLE. WSL blind spot: a line-oriented
  program inside the VM is invisible to the Windows Job and sets no alt-screen, so a
  WSL tab with no 133 this session is UNKNOWN, never IDLE (this falls out of the
  three-state model automatically).

Rider policy mapping (implemented by #83/#84/#86, recorded here for reference):
- Auto-CD (unsolicited): inject only on IDLE; UNKNOWN stays suppressed (continuity
  with #83 -- Auto-CD stays off in ConPTY until shell integration is present).
- Saved-command run and Project/File Dir buttons (user-initiated): IDLE -> inject;
  UNKNOWN -> #84 policy (warn-and-proceed/refuse); BUSY -> refuse/warn.
- Paste: ungated.

Notes verified for this codebase:
- Threading: OSC parsing runs on the main thread (FlushOutputBuffer <- render timer),
  and consumers (button clicks, Auto-CD events, palette) are also main-thread, so the
  prompt-state write and the gate read are same-thread -- no cross-thread publication
  or TOCTOU window. (If parsing ever moves off the main thread, revisit.)
- Per-tab: the gate is per-frame (own parser/screen/Job/markers); consumers must query
  the target tab's gate (e.g. Auto-CD all-tabs checks each tab; a shell-targeted saved
  command checks that shell's tab).
- Half-typed-line ("any keystroke since last B") remains a deferred refinement.

Implementation notes:
- Replace the Boolean with `TShellIdleState = (sisUnknown, sisIdle, sisBusy)`.
- `TScreenBuffer.IdleState(AForegroundChild)`: BUSY if alt-screen or PromptState C or
  AForegroundChild; IDLE only if PromptState B; else UNKNOWN.
- Add `633` alongside `133` in `DispatchOSC`.
- `TframeCmdShell.ShellIdleState: TShellIdleState` (legacy -> sisIdle).

Acceptance criteria:
- [ ] Gate is three-state (Idle / Busy / Unknown), not Boolean
- [ ] Only OSC 133/633 asserts Idle; the alt-screen/Job fallback only asserts Busy or leaves Unknown, never Idle
- [ ] Idle only in the input window (after B, before C); A and D are not Idle
- [ ] Any Busy signal (alt-screen, 133/633 C, Job child > 1) overrides an Idle marker
- [ ] OSC 633 A/B/C/D handled like 133; trailing params tolerated
- [ ] A WSL tab with no markers this session never returns Idle
- [ ] Unit tests cover the three-state matrix and the tightened FSM
